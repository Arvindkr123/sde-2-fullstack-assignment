**Tool used:** Claude (claude-sonnet-4-6 via Claude Code CLI)

---

## How it was used

- **Initial code review:** Asked Claude to read each source file and enumerate potential bugs, concurrency issues, and security gaps. This surfaced the full list quickly rather than reading line-by-line manually.
- **Lua script authoring:** Asked Claude to draft the atomic `CHECK_AND_INCREMENT` Lua script for Redis, then reviewed it for correctness before accepting.
- **Frontend scaffolding:** Claude generated the full React + Vite + TypeScript structure (package.json, tsconfig, vite.config, routing, pages). The generated code was reviewed for type correctness and API contract alignment.
- **Submission documents:** Drafts for FINDINGS.md and DECISIONS.md were generated by Claude and then edited for accuracy.

## Prompts that worked well

**1. Bug enumeration**
> "Read all the backend source files and give me a complete list of correctness bugs, concurrency bugs, security issues, and risky patterns. Include file:line for each."

This produced the full list of 7 issues in one pass, saving significant manual review time. The output was specific enough to act on directly.

**2. Atomic Redis pattern**
> "I need an ioredis Lua eval that atomically checks two rate-limit counters and only increments both if neither limit is exceeded. Show the Lua script and the TypeScript call."

The output was correct. Reviewing it: the Lua `GET` returns `false` for missing keys (not `nil`), which the script handles with `dRaw and tonumber(dRaw) or 0` — a subtle Lua idiom I verified before accepting.

## Where AI led me astray

**cancelDelayedJobs — wrong fix suggested first**

Claude's initial suggestion for fixing the `getDelayed(0, 5000)` truncation was to paginate in a loop:

```ts
while (true) {
  const batch = await sendQueue.getDelayed(start, start + 99);
  if (batch.length === 0) break;
  for (const job of batch) { /* check sequence_id via DB */ }
  start += 100;
}
```

This is technically correct but O(total queue depth) — it scans every delayed job across all sequences, doing one DB query per job. For a large queue this would be extremely slow and would hold a lock-like scan on every pause operation.

The right fix is the reverse: query the DB for *this sequence's* pending email IDs, then look up each BullMQ job by its deterministic ID (`se-<id>`). This is O(n) in the sequence's own emails, independent of queue depth.

I caught this by thinking about the data-access pattern rather than just "does it produce the right answer." The AI produced a correct-but-naive solution; the better approach required reasoning about scale.
